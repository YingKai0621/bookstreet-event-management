## 1. Purpose

This overlay extends the existing `notifications` table. It does not create a second inbox table,
NotificationType table, sender relationship, preference store, delivery-attempt table, or outbox.

The design makes the role audience durable, supports the approved Partner and Organizer references, and
preserves all existing Participant rows and six types.

## 2. Existing baseline

V10 created `notifications`; V12 added `badge_id` and `BADGE_UNLOCKED`. The current table has 12 columns,
one recipient/deduplication unique constraint, strict type/reference checks, owner-created and owner-unread
indexes, and one Badge reference index.

V10 and V12 are immutable. Sprint 10 uses one new migration.

## 3. Target physical columns

| Column | Type | Null | Purpose |
| --- | --- | --- | --- |
| `notification_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | Stable Notification identity |
| `recipient_user_id` | `BIGINT` | No | Recipient User FK |
| `recipient_role` | `VARCHAR(20)` | No | Exact role audience |
| `notification_type` | `VARCHAR(60)` | No | Closed role-compatible type |
| `event_id` | `BIGINT` | Yes | Event cancellation reference |
| `activity_id` | `BIGINT` | Yes | Activity change/cancellation reference |
| `certificate_id` | `BIGINT` | Yes | Certificate reference |
| `badge_id` | `BIGINT` | Yes | Badge reference |
| `partner_event_application_id` | `BIGINT` | Yes | Partner application reference |
| `booth_request_id` | `BIGINT` | Yes | Booth request and re-selection reference |
| `activity_proposal_id` | `BIGINT` | Yes | Activity proposal reference |
| `activity_request_id` | `BIGINT` | Yes | Activity change/cancellation request reference |
| `deduplication_key` | `VARCHAR(200)` | No | Stable transition identity |
| `title` | `VARCHAR(200)` | No | Server-owned display snapshot |
| `message` | `TEXT` | No | Server-owned display snapshot |
| `created_at` | `TIMESTAMPTZ` | No | Owning transition time |
| `read_at` | `TIMESTAMPTZ` | Yes | First read time; null means unread |

No generic `reference_type`, unvalidated numeric reference, JSON payload, URL, sender, priority, or delivery
channel is stored.

The API's nullable `contextEventId` is derived at query time through the validated reference relationship.
It is not a duplicated column and does not weaken the exact-reference constraint.

## 4. Keys and foreign keys

Existing primary key and existing foreign keys remain. The migration adds:

- `fk_notifications_partner_event_application` to `partner_event_applications`
- `fk_notifications_booth_request` to `booth_requests`
- `fk_notifications_activity_proposal` to `activity_proposals`
- `fk_notifications_activity_request` to `activity_requests`

Every FK uses `ON DELETE RESTRICT`, matching the durable-history policy.

The existing unique constraint is replaced with:

```text
UNIQUE (recipient_user_id, recipient_role, deduplication_key)
```

This permits one transition to notify two distinct role audiences of the same multi-role User while still
preventing a duplicate within one inbox.

## 5. Role values

`ck_notifications_recipient_role` accepts exactly:

```text
PARTICIPANT
PARTNER
ORGANIZER
ADMIN
```

Existing rows are backfilled to `PARTICIPANT` before the column becomes non-null. The migration does not
infer role from current `user_roles`, because existing rows were created by the Participant contract and
must remain in that audience even if the User now has multiple roles.

## 7. Type, role, and reference constraint

One replacement `ck_notifications_type_role_reference` constraint enforces all three dimensions.

For every row, exactly one reference column is non-null and it matches the type:

| Audience and type family | Required reference |
| --- | --- |
| Participant Activity types | `activity_id` |
| Participant Event cancellation | `event_id` |
| Participant Certificate types | `certificate_id` |
| Participant Badge unlock | `badge_id` |
| Partner application status | `partner_event_application_id` |
| Partner Booth request status | `booth_request_id` |
| Partner proposal status | `activity_proposal_id` |
| Partner Activity request outcome | `activity_request_id` |
| Partner Event cancellation | `event_id` |
| Partner Activity cancellation | `activity_id` |
| Organizer new application | `partner_event_application_id` |
| Organizer new Booth request or re-selection | `booth_request_id` |
| Organizer proposal submitted | `activity_proposal_id` |
| Organizer Activity request work item | `activity_request_id` |

All other reference columns must be null. Participant types require `PARTICIPANT`, Partner types require
`PARTNER`, and Organizer types require `ORGANIZER`.

Existing title, message, deduplication-key, and read-time checks remain. `read_at` continues to require
`read_at >= created_at`.

## 8. Indexes

The old owner-only query indexes are replaced with role-aware indexes:

```text
idx_notifications_recipient_role_created
    (recipient_user_id, recipient_role, created_at DESC, notification_id ASC)

idx_notifications_recipient_role_unread
    (recipient_user_id, recipient_role, created_at DESC, notification_id ASC)
    WHERE read_at IS NULL

idx_notifications_recipient_role_read
    (recipient_user_id, recipient_role, read_at DESC NULLS LAST, notification_id ASC)
```

Reference indexes are required for each newly added FK:

```text
idx_notifications_partner_event_application
idx_notifications_booth_request
idx_notifications_activity_proposal
idx_notifications_activity_request
```

Existing Event, Activity, Certificate, and Badge reference indexes remain where already present or are
added only if the applied schema lacks the FK-supporting index. No speculative text-search index is added.

## 9. Migration sequence

The migration must perform this order:

1. add nullable `recipient_role`
2. backfill every existing row to `PARTICIPANT`
3. set `recipient_role` non-null
4. add the four nullable reference columns and foreign keys
5. replace the old type/reference checks with the combined role/type/reference check
6. replace the old recipient/deduplication unique constraint with the role-aware unique constraint
7. replace owner-only query indexes with the role-aware created/unread indexes and add the read-time index
8. add required reference indexes
9. preserve every existing identity, type, reference, title, message, `created_at`, and `read_at`

The migration adds no seed Notification and changes no User role assignment.

## 10. Transaction and concurrency boundary

### 10.1 Creation

Producer order follows the owning domain lock order, then inserts Notification last before commit. The
writer uses the role-aware unique constraint as the final retry guard. `ON CONFLICT DO NOTHING` may target
the role-aware identity only after validation has proved the role/type/reference combination.

### 10.2 Mark one

Mark-one uses a conditional database update under owner and role predicates. It must not use an unlocked
read followed by a mutable entity assignment. If the row is already read, the command returns its existing
timestamp. If it belongs to another User or role, it returns not-found.

### 10.3 Mark all

Mark-all uses one conditional update for the authenticated User and endpoint role where `read_at IS NULL`.
All rows changed by the command receive one backend timestamp. Existing values remain untouched.

## 11. Required database verification

- clean V1 through the new migration
- upgrade from V15 with unread and read Participant rows
- Hibernate `ddl-auto: validate`
- exact backfill to `PARTICIPANT`
- preservation of original ids, references, created time, and read time
- rejection of unsupported role, type, reference, and role/type combinations
- rejection of duplicate User/role/deduplication identity
- acceptance of the same User/key under two different roles when each type is role-compatible
- every new FK and `ON DELETE RESTRICT`
- role-aware ordering and unread indexes
- default created-time ordering uses `notification_id ASC`, and read-time ordering keeps nulls last
- no Admin row accepted because Sprint 10 defines no Admin type

## 12. Explicit physical exclusions

This overlay adds no:

- second notification table
- NotificationType, channel, preference, template, subscription, delivery, or outbox table
- sender, actor, priority, expiration, archive, delete, or payload column
- generic unvalidated reference pair
- Feedback, Heritage, Attendance, PointTransaction, Payment, or UserRole reference
- Redis key or cache
- production data seed

## 14. Overlay conclusion

Sprint 10 changes one existing table by adding one audience column and four approved domain references.
It preserves the implemented Participant history, makes multi-role isolation enforceable in PostgreSQL,
and supports bounded Partner and Organizer producers without creating a generic messaging platform.
