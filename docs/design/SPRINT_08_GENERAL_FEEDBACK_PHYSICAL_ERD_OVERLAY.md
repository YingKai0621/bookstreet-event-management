## 1. Purpose

This document records the physical database overlay implemented for the Sprint 08 General Feedback
vertical slice by `V14__create_sprint8_general_feedback_schema.sql`.

The applied table supports only `BOOK_STREET` and `EVENT`, exactly as approved by the Sprint 8 Use
Case Specification and API Contract. The product decision dated `2026-11-01` confirms that
Heritage content remains independent from General Feedback. The main Physical ERD report now
records the applied V14 schema.

## 2. Source-of-truth alignment

### 2.1 Business baseline retained

The current business baseline allows General Feedback to target only Book Street or Event:

- `BOOK_STREET`: feedback about the Book Street as a whole.
- `EVENT`: feedback about one persisted Event.

Heritage content is managed and displayed independently. It is not a General Feedback target and
does not create a relationship between `general_feedbacks` and `heritage_contents`.

### 2.2 Approved Sprint 08 decisions represented here

- General Feedback is separate from Activity Rating.
- General Feedback has no star score or satisfaction score.
- A Guest may optionally provide a name and email; phone number is not collected.
- All verified `ORGANIZER` accounts share one Feedback queue.
- Feedback statuses are exactly `NEW`, `IN_PROGRESS` and `RESOLVED`.
- The legal transitions are `NEW -> IN_PROGRESS`, `IN_PROGRESS -> RESOLVED` and `RESOLVED -> IN_PROGRESS`.
- Viewing a Feedback item does not change its status.
- Resolving requires a nonblank internal note.
- The latest handling Organizer and relevant timestamps are retained.
- Reopening clears the resolved time but retains the Feedback and internal note.
- Sprint 08 does not introduce a transition-history table.
- The Guest receives submission acknowledgement only; no reply, email, notification or public resolution result is persisted.
- Anonymous throttling is enforced by the application layer and does not persist raw IP addresses.

## 3. Implemented table

### 3.1 Table name

`general_feedbacks`

### 3.2 Physical columns

| Column | Physical type | Null | Default | Purpose |
| --- | --- | --- | --- | --- |
| `general_feedback_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | Identity | Primary key. |
| `submitted_by_user_id` | `BIGINT` | Yes | None | Optional authenticated submitter; anonymous submissions remain `NULL`. |
| `target_type` | `VARCHAR(20)` | No | None | Sprint 08 values: `BOOK_STREET`, `EVENT`. |
| `event_id` | `BIGINT` | Yes | None | Required only when `target_type = 'EVENT'`. |
| `guest_name` | `VARCHAR(100)` | Yes | None | Optional normalized display name supplied by the Guest. |
| `contact_email` | `VARCHAR(255)` | Yes | None | Optional normalized lowercase contact email. No outbound response is sent in Sprint 08. |
| `message` | `TEXT` | No | None | Guest Feedback content. |
| `status` | `VARCHAR(20)` | No | `'NEW'` | Workflow status. |
| `internal_note` | `VARCHAR(1000)` | Yes | None | Organizer-only handling note; mandatory when resolved. |
| `last_handled_by_user_id` | `BIGINT` | Yes | None | Organizer who performed the latest workflow transition. |
| `handling_started_at` | `TIMESTAMPTZ` | Yes | None | Start time of the current handling cycle. Reset when a resolved item is reopened. |
| `submitted_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Submission time. |
| `updated_at` | `TIMESTAMPTZ` | No | `CURRENT_TIMESTAMP` | Last persisted workflow update time. |
| `resolved_at` | `TIMESTAMPTZ` | Yes | None | Resolution time; cleared on reopen. |

### 3.3 Deliberately excluded columns

The Sprint 08 table does not include:

- `heritage_content_id`, because Heritage is not a General Feedback target.
- `subject`, because the approved Guest flow requires a message rather than a separate subject field.
- rating or satisfaction fields, because Activity Rating is a separate feature.
- phone number.
- public reply or response-delivery fields.
- target display-name snapshots.
- raw IP address, device fingerprint or CAPTCHA data.
- soft-delete fields.
- duplicated Event owner or Organizer identifiers.

## 4. Keys and relationships

### 4.1 Primary key

- `pk_general_feedbacks` on `general_feedback_id`.

### 4.2 Foreign keys

| Constraint | From | To | Delete behavior |
| --- | --- | --- | --- |
| `fk_general_feedbacks_submitted_by_user` | `submitted_by_user_id` | `users.user_id` | `ON DELETE RESTRICT` |
| `fk_general_feedbacks_event` | `event_id` | `events.event_id` | `ON DELETE RESTRICT` |
| `fk_general_feedbacks_last_handled_by_user` | `last_handled_by_user_id` | `users.user_id` | `ON DELETE RESTRICT` |

`last_handled_by_user_id` identifies the latest actor only. It is not an ownership field and must not be used to restrict which Organizer can view or handle Feedback.

### 4.3 Logical relationship view

```text
users 1 -------- 0..* general_feedbacks (optional submitter)
users 1 -------- 0..* general_feedbacks (latest handling Organizer)
events 1 ------- 0..* general_feedbacks (EVENT target only)

BOOK_STREET target: target_type = BOOK_STREET and event_id IS NULL
EVENT target:       target_type = EVENT       and event_id IS NOT NULL
```

## 5. Check constraints

The following names and expressions define the expected migration shape. Minor SQL formatting changes are allowed; weakening the rules is not.

### 5.1 Target constraints

`ck_general_feedbacks_target_type`

```sql
target_type IN ('BOOK_STREET', 'EVENT')
```

`ck_general_feedbacks_target_reference`

```sql
(target_type = 'BOOK_STREET' AND event_id IS NULL)
OR
(target_type = 'EVENT' AND event_id IS NOT NULL)
```

This prevents orphan target combinations without inventing a singleton Book Street row solely for Feedback.

### 5.2 Status constraint

`ck_general_feedbacks_status`

```sql
status IN ('NEW', 'IN_PROGRESS', 'RESOLVED')
```

The database constrains valid stored states. The service layer remains responsible for enforcing legal state transitions and authorization.

### 5.3 Text constraints

Proposed bounds for the Sprint 08 Use Case and API documents:

- `guest_name`: when present, trimmed, normalized for repeated whitespace, length `1..100`.
- `contact_email`: when present, trimmed, lowercase, length `3..255`; full email syntax is validated by the application.
- `message`: trimmed while preserving intentional internal line breaks, length `10..2000`.
- `internal_note`: when present, trimmed, length `1..1000`.

Recommended constraint names:

- `ck_general_feedbacks_guest_name`
- `ck_general_feedbacks_contact_email`
- `ck_general_feedbacks_message`
- `ck_general_feedbacks_internal_note`

The final Use Case Specifications and API Contract must use the same limits before the migration is authored.

### 5.4 Workflow-state consistency

`ck_general_feedbacks_workflow_state`

The stored fields must satisfy these state invariants:

| Status | Latest handler | Handling started | Resolved time | Internal note |
| --- | --- | --- | --- | --- |
| `NEW` | `NULL` | `NULL` | `NULL` | `NULL` |
| `IN_PROGRESS` | Required | Required | `NULL` | Optional; retained after reopen |
| `RESOLVED` | Required | Required | Required | Required and nonblank |

The intended logical expression is:

```sql
(
    status = 'NEW'
    AND last_handled_by_user_id IS NULL
    AND handling_started_at IS NULL
    AND resolved_at IS NULL
    AND internal_note IS NULL
)
OR
(
    status = 'IN_PROGRESS'
    AND last_handled_by_user_id IS NOT NULL
    AND handling_started_at IS NOT NULL
    AND resolved_at IS NULL
)
OR
(
    status = 'RESOLVED'
    AND last_handled_by_user_id IS NOT NULL
    AND handling_started_at IS NOT NULL
    AND resolved_at IS NOT NULL
    AND internal_note IS NOT NULL
)
```

### 5.5 Timestamp consistency

`ck_general_feedbacks_timestamps`

The migration must ensure:

- `submitted_at <= updated_at`.
- `handling_started_at`, when present, is not earlier than `submitted_at` and not later than `updated_at`.
- `resolved_at`, when present, is not earlier than `handling_started_at` and not later than `updated_at`.

Application writes should use one transaction timestamp for all fields changed by a transition.

## 6. Workflow writes

### 6.1 Guest submission

On creation:

- `status = 'NEW'`.
- `last_handled_by_user_id`, `handling_started_at`, `resolved_at` and `internal_note` are `NULL`.
- `submitted_at` and `updated_at` are set to the same time.
- `submitted_by_user_id` is populated only when the submitter is authenticated and the API intentionally associates the submission.

### 6.2 Start handling: `NEW -> IN_PROGRESS`

In one transaction:

- set `status = 'IN_PROGRESS'`;
- set `last_handled_by_user_id` to the current Organizer;
- set `handling_started_at` to the transition time;
- set `updated_at` to the transition time;
- leave `resolved_at = NULL`.

### 6.3 Resolve: `IN_PROGRESS -> RESOLVED`

In one transaction:

- require and store a normalized nonblank `internal_note`;
- set `status = 'RESOLVED'`;
- set `last_handled_by_user_id` to the current Organizer;
- set `resolved_at` and `updated_at` to the transition time;
- preserve `handling_started_at` for the current handling cycle.

### 6.4 Reopen: `RESOLVED -> IN_PROGRESS`

In one transaction:

- set `status = 'IN_PROGRESS'`;
- set `last_handled_by_user_id` to the current Organizer;
- reset `handling_started_at` to the reopen time;
- clear `resolved_at`;
- retain the existing `internal_note`;
- set `updated_at` to the reopen time.

Because Sprint 08 deliberately has no transition-history table, reopening replaces the previous resolved timestamp. The retained internal note provides handling context but is not an audit log.

## 7. Index plan

The minimum approved indexes are:

```sql
CREATE INDEX idx_general_feedbacks_queue
    ON general_feedbacks (submitted_at DESC, general_feedback_id DESC);

CREATE INDEX idx_general_feedbacks_status_queue
    ON general_feedbacks (status, submitted_at DESC, general_feedback_id DESC);

CREATE INDEX idx_general_feedbacks_event_queue
    ON general_feedbacks (event_id, status, submitted_at DESC, general_feedback_id DESC)
    WHERE event_id IS NOT NULL;
```

These support:

- the shared Organizer queue with deterministic newest-first pagination;
- status filtering;
- Event filtering combined with status;
- stable cursor or offset ordering using `general_feedback_id` as the tie-breaker.

No index is proposed for free-text contains search in Sprint 08. The initial data volume does not justify adding PostgreSQL extensions or specialized text indexes. Query plans should be reviewed before adding more indexes.

## 8. Access and privacy implications

- The database does not model per-Organizer Feedback ownership.
- Authorization is applied by the service layer: any verified active `ORGANIZER` may access the shared queue.
- Existing Event owner restrictions remain unchanged for Event management operations.
- `contact_email` is private contact data and must not appear in public responses or logs.
- `internal_note` and handling identity are Organizer-only data.
- The public submission receipt must expose only the minimum identifier and acknowledgement information defined by the API Contract.
- Anonymous throttling state belongs in bounded process-local volatile memory. Redis remains
  Session-only, and raw IP addresses must not be added to PostgreSQL, limiter keys or logs for this
  feature.

## 9. Migration and rollout result

1. V14 was confirmed available on the implementation branch.
2. `V14__create_sprint8_general_feedback_schema.sql` created the table, constraints, foreign keys
   and indexes in one focused migration.
3. No production or demo Feedback row was added by the migration.
4. Clean V1-to-V14 migration, V13-to-V14 upgrade and Hibernate validation are covered by focused
   automated tests.
5. V1 through V14 are now immutable.

Future Heritage persistence must remain independent. No later migration may add
`heritage_content_id` or `HERITAGE` to `general_feedbacks` under the current business baseline.
The Sprint 08 migration remains immutable.

## 10. Validation checklist

The migration and persistence tests derived from this overlay must cover at least:

- valid anonymous `BOOK_STREET` Feedback;
- valid authenticated or anonymous `EVENT` Feedback;
- rejection of unsupported target types;
- rejection of mismatched `target_type` and `event_id`;
- rejection of unknown Event references;
- rejection of invalid statuses;
- rejection of blank or out-of-range messages;
- rejection of a resolved row without a handler, handling time, resolution time or internal note;
- rejection of inconsistent timestamps;
- successful `NEW -> IN_PROGRESS -> RESOLVED` persistence;
- successful `RESOLVED -> IN_PROGRESS` reopen while retaining `internal_note` and clearing `resolved_at`;
- deterministic newest-first Organizer queue ordering;
- clean-install and `V13`-upgrade Flyway validation.
