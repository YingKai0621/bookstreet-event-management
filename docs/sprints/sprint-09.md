## 1. Purpose

Sprint 09 turns the existing Heritage presentation and Organizer placeholder screen into one small,
durable public-content workflow:

1. a verified Organizer creates and maintains Heritage content in a shared management area
2. an Organizer explicitly publishes or archives that content
3. Guests and Participants browse only published Heritage content
4. public detail links use one stable public identifier
5. the existing public and Organizer screens use real PostgreSQL-backed APIs

Heritage remains supporting public content. This Sprint does not create an independent heritage
collection, conservation, artifact, or approval-management domain.

## 5. Heritage domain baseline

### 5.1 Identity

Each Heritage content record has:

- an internal numeric `heritageContentId` used for persistence and Organizer operations
- one generated public `publicCode` used only as the stable public detail-route identity

`publicCode` is generated by the backend from the normalized title, case-insensitively unique, and
immutable after creation. Organizer requests never accept this technical value. The generator removes
Vietnamese diacritics, creates the canonical uppercase hyphenated form and appends a numeric suffix when
the title-derived code is already used. The Physical ERD overlay continues to lock its format and length.

Public routes must not depend only on the internal numeric id. The frontend must stop using a list item id
as an undocumented slug.

### 5.2 Durable content

The first Sprint 09 persistence model contains only:

- `publicCode`
- normalized plain-text `title`
- optional normalized plain-text `summary`
- required normalized plain-text `content`
- optional `imageUrl`
- optional `locationText`
- `status`
- optional `publishedAt`
- `createdAt`
- `updatedAt`

The database overlay defines exact physical types, limits, constraints, indexes, defaults, and timestamps.
The API Contract must apply compatible normalization and validation before persistence and define stable
error codes.

The existing frontend fields for English translations, province, category, period, highlights, source,
license, image metadata, map coordinates, QR status, view count, and scan count are presentation debt. They
must not become durable fields in this Sprint.

### 5.3 Shared Organizer management

Every authenticated verified Organizer manages the same Heritage collection. There is no per-Organizer
ownership filter and no Event relationship.

Because multiple Organizers can edit the same record, every update, lifecycle command, and draft delete uses
the last observed `updatedAt` as `expectedUpdatedAt`. A stale command returns conflict and does not overwrite
the newer row.

Organizer list and detail responses may contain the full approved Heritage content shape. Public responses
must contain only public display fields and must not expose internal numeric ids or management metadata that
is not required for display.

Callers without effective verified Organizer authority cannot access Organizer mutation operations. This
includes anonymous, Participant-only, Partner-only, Admin-only, disabled, and unverified accounts. A
multi-role account is evaluated by its effective Organizer authority rather than blocked by another role.

### 5.4 Lifecycle

The only statuses are:

- `DRAFT`
- `PUBLISHED`
- `ARCHIVED`

New content always starts as `DRAFT`. A create request cannot bypass validation by asking for another
initial status.

The legal transitions are:

- `DRAFT -> PUBLISHED`
- `PUBLISHED -> ARCHIVED`
- `ARCHIVED -> PUBLISHED`

There is no transition from `PUBLISHED` or `ARCHIVED` back to `DRAFT`. Content fields may be edited while
the record is in any status, but an update does not silently change status.

Status changes use explicit lifecycle commands. Generic create or content-update requests cannot assign a
different status directly.

The first transition to `PUBLISHED` sets `publishedAt`. Archiving and republishing preserve the original
`publishedAt`. Every accepted content or lifecycle change updates `updatedAt`.

`DRAFT` requires `publishedAt` to be null. `PUBLISHED` and `ARCHIVED` require `publishedAt` to be non-null.

Create and update validation keeps every draft structurally valid. Publish defensively revalidates the
persisted required fields. A defective or stale record remains a draft and produces no partial lifecycle
change.

### 5.5 Deletion and history

Hard delete is allowed only when the record is `DRAFT` and has never been published. A published or archived
record must be archived or remain archived. It cannot be hard-deleted through Sprint 09 APIs.

The Organizer UI must not show a destructive delete action for `PUBLISHED` or `ARCHIVED` content. It shows
the appropriate archive or republish action instead.

### 5.6 Public visibility

Guests and authenticated users may access only `PUBLISHED` Heritage content.

- the public list returns only `PUBLISHED` records
- public detail resolves one `PUBLISHED` record by canonical `publicCode`
- `DRAFT`, `ARCHIVED`, unknown, and malformed identifiers do not reveal private content
- archiving removes the item from public list and detail access immediately after the mutation succeeds
- republishing restores public access using the same `publicCode`

Public list ordering must be deterministic. The exact ordering and pagination shape belong to the API
Contract.

### 5.7 Image handling

`imageUrl` is optional. Organizer uploads accept validated JPG, PNG, or WebP files up to 5 MB. The backend
stores generated filenames in bounded local media storage and persists only the resulting approved
`/assets/heritage/uploads/` URL. Data URLs, blob URLs, caller filesystem paths, and raw image bytes are
never persisted in PostgreSQL. This upload path is not a general asset library or external storage provider.

### 5.8 Public navigation behavior

The public detail URL continues to use the stable generated `publicCode`, but Heritage screens display no
QR block and no technical code label. The database continues to store no QR token, image, status, or scan
counter.

## 6. Organizer experience baseline

The existing `/organizer/public-content` route remains the Heritage management entry point unless the API
Contract and implementation plan identify a smaller compatible route change.

The real Organizer experience must:

- load the shared collection from the backend on initial entry
- support server-owned search, status filter, deterministic sort, and pagination
- distinguish loading, empty, filtered-empty, error, and populated states
- create a validated draft through the real API
- edit content without changing lifecycle implicitly
- expose publish, archive, republish, and eligible draft-delete actions according to status
- require confirmation for archive and hard delete
- preserve user input after a recoverable validation or conflict response
- detect stale `updatedAt`, explain the conflict, and offer a safe reload instead of overwriting newer data
- refresh or reconcile state after a successful mutation
- never show success when the API rejected a command
- replace lower-case `published`, `draft`, and `hidden` assumptions with the canonical contract
- remove or hide fields that are outside the durable Sprint 09 model
- hide the generated public code from the form and provide image selection, preview, replacement and removal

The word `hidden` must not be used as a fourth lifecycle status. Its intended behavior is represented by
`ARCHIVED`.

## 7. Public experience baseline

The existing Heritage section, `/di-san` list route, and `/di-san/:publicCode` detail route remain the public
experience.

The real public experience must:

- load published Heritage content from the backend without mock or local fallback data
- distinguish loading, empty, not-found, and server-error states
- support opening a detail URL directly without first loading the Landing Page collection
- use `publicCode` consistently in links and route resolution
- remove the current endless-loading behavior for a valid empty collection
- avoid showing draft or archived content from stale client state
- preserve the current visual direction where it maps to approved data
- degrade optional image, summary, and location fields safely
- hide technical public-code labels and omit Heritage QR presentation

The frontend may adapt the minimal API model into display-only values. It must not manufacture business
statuses, analytics, ownership, or unpublished content.

## 8. Security and privacy baseline

- public list and detail reads are anonymous and read-only
- Organizer list, detail, and mutations require effective verified Organizer authority
- authorization comes from the authenticated Session and never from a caller-supplied role or User id
- unknown or unpublished public content does not reveal whether a private record exists
- validation and conflict responses do not expose SQL, stack traces, filesystem paths, or credentials
- content rendering must not execute stored HTML or scripts
- public and Organizer mutations continue to use the shared CSRF contract
- logging must not include Session cookies, CSRF tokens, credentials, or full request bodies
- the Sprint adds no Redis Heritage cache, lock, queue, or temporary content store

## 9. Data and migration baseline

The Heritage Physical ERD overlay must define one `heritage_contents` table compatible with the approved
domain fields. It must specify at least:

- primary key
- case-insensitive unique public-code enforcement
- status check constraint
- nonblank content constraints that belong safely in PostgreSQL
- publication timestamp invariant
- created and updated timestamp defaults
- indexes for public published ordering and Organizer status or search access
- deletion behavior and the absence of a General Feedback foreign key

The implementation created one production migration after rechecking the latest migration on updated
`main`. V15 is now applied and immutable.

No demo Heritage rows are inserted by the production migration. Demo data, if later required, must use an
approved isolated seed path and must not contain credentials or personal data.

## 10. Acceptance Criteria baseline

### 10.1 Organizer management

1. `AC-O09-S9-01`: every verified Organizer can open the shared Heritage management list through a real
   authenticated API.
2. `AC-O09-S9-02`: the list supports the approved server-side search, status, sorting, and pagination
   contract with deterministic results.
3. `AC-O09-S9-03`: creating valid content creates exactly one `DRAFT` record with a backend-generated,
   unique and immutable `publicCode`.
4. `AC-O09-S9-04`: invalid, blank, oversized, malformed, or unsupported create and image-upload fields
   create no row and return the stable API error defined by the contract.
5. `AC-O09-S9-05`: an Organizer can update approved content fields without changing `publicCode` or status
   implicitly. A stale `expectedUpdatedAt` returns conflict and preserves the newer record.
6. `AC-O09-S9-06`: publishing a valid draft changes only that record to `PUBLISHED`, sets its first

7. `AC-O09-S9-07`: publishing an invalid draft, sending an illegal transition, or using a stale

8. `AC-O09-S9-08`: archiving a published record changes it to `ARCHIVED` and removes it from public list and

9. `AC-O09-S9-09`: republishing an archived record restores public visibility with the same `publicCode` and
   original `publishedAt`.
10. `AC-O09-S9-10`: a never-published draft may be hard-deleted only after explicit confirmation and a
    matching `expectedUpdatedAt`.
11. `AC-O09-S9-11`: published and archived records reject hard delete and remain durable.
12. `AC-O09-S9-12`: every verified Organizer sees accepted changes because the collection is shared rather
    than owner-filtered.
13. `AC-O09-S9-13`: callers without effective verified Organizer authority, including Admin-only accounts,

## 14. Product decisions recorded in this Sprint

- Organizer is the only Heritage management actor in Sprint 09
- every verified Organizer manages the same shared collection
- Admin has no Heritage API or UI in this Sprint
- Heritage is supporting public content rather than an independent management domain
- Heritage is permanently separate from General Feedback
- the lifecycle is `DRAFT`, `PUBLISHED`, and `ARCHIVED`
- public access is limited to `PUBLISHED` content
- `publicCode` is the stable public identity and cannot be edited after creation
- published or archived content is never hard-deleted
- only a never-published draft may be hard-deleted
- persisted fields follow the minimal Physical ERD direction
- Heritage QR presentation is omitted and no QR data is persisted
- map coordinates, analytics, bilingual persistence, reports, and Admin management are excluded

These decisions are approved and frozen for Sprint 09 implementation. Semantic changes require a new
documentation review before code changes.
